# 亚马逊授权与自动上架实操

适用版本：1.0.0。官方资料核对日期：2026-11-14。平台页面会调整，以下同时提供功能名称与官方链接。

本页以管理自己公司的 Seller Central 账号、美国站、单个新 SKU 为主线。公开应用服务其他卖家另见第 11 节。真实操作由你的运行环境执行，本页不会要求将凭据发到聊天或 GitHub。

## 1. 先区分两层授权

| 授权 | 在哪里完成 | 决定什么 |
| --- | --- | --- |
| Amazon 应用角色及卖家授权 | Solution Provider Portal / Seller Central | 应用是否能代表该卖家调用对应接口 |
| 项目发布授权 | 私有配置 writePolicy 或一次性计划授权 | Agent 能否正式提交，以及商品、价格、数量、期限和次数范围 |

Amazon 授权成功不会自动开启本项目写入；把 writePolicy 设为 bounded 也不会获得 Amazon 权限。两层都满足，才会发送正式提交。

## 2. 准备自己的开发者身份与应用

### 2.1 自用还是服务其他卖家

仅用于自己公司的账号，按 Amazon 私有开发者/私有应用路径申请。准备实际组织信息、用途、需要的数据和安全控制，如实完成审核。不要把需要服务其他公司的产品登记成仅供自己使用的应用。[官方私有开发者注册说明](https://developer-docs.amazon/sp-api/docs/register-as-a-private-developer)

入口通常为 Seller Central 的 **Apps and Services → Develop Apps**；已迁移的账号可在 [Solution Provider Portal](https://solutionproviderportal.amazon.com) 的 Developer Profile/Develop Apps 功能中处理。以实际账号页面和当前官方指引为准。

### 2.2 取得角色并建立生产应用

开发者资料及所需角色获批后，在门户中选择 **Add new app client**：填写应用名称，API 类型选 SP-API，应用环境选 Production，并选择已批准、实际需要的角色。Sellers/Vendors 的选项按经营类型填写，本项目主线是 Seller。[官方生产应用注册步骤](https://developer-docs.amazon/sp-api/docs/onboarding-step-7-register-your-first-production-application)

上架核心使用 Product Type Definitions 和 Listings Items；根据 [官方角色映射](https://developer-docs.amazon/sp-api/docs/role-mappings) 确认 **Product Listing** 角色。FBA 库存和不同报表还有各自权限要求，不要为了一个上架任务盲目申请全部数据角色。

开发者角色获批、应用勾选相应角色、目标卖家授权是需要分别确认的环节。GitHub 仓库公开与 Amazon 应用是否获批没有对应关系。

## 3. 获取 LWA 客户端信息与卖家刷新令牌

### 3.1 客户端信息

在 Develop Apps 中找到你的应用，进入 **Edit app → LWA credentials → View**，取得：

- LWA client ID，写入 AMAZON_LWA_CLIENT_ID。
- LWA client secret，写入 AMAZON_LWA_CLIENT_SECRET。

Application ID 和 LWA client ID 是不同字段，不能互相代填。[官方凭据查看方法](https://developer-docs.amazon/sp-api/docs/viewing-your-application-information-and-credentials)

### 3.2 为自己的卖家账号自授权

使用目标 Seller Central 账号的主用户身份，在门户或 Develop Apps 找到应用的 **Authorize / Authorize app / Manage Authorizations** 功能。核对目标账号及站点，选择 Authorize app，取得该账号对应的 **LWA refresh token**。

将它安全保存为 AMAZON_LWA_REFRESH_TOKEN。私有应用可在 draft 状态自授权，不需要为自用而上架到应用商店。主用户要求、跨区域账号与自授权细节以 [官方自授权说明](https://developer-docs.amazon/sp-api/docs/self-authorization) 和 [授权工作流指引](https://developer-docs.amazon/sp-api/docs/onboarding-step-6-set-up-the-authorization-workflow) 为准。

每个令牌与被授权卖家相对应。多个卖家不要共用一份配置和状态；首版一个 MCP 实例只配置一个卖家、一个目标站点。重新生成 refresh token 不应被当成已撤销旧令牌的证明；撤销授权或处理泄露须使用平台实际提供的管理流程。

### 3.3 程序运行时做什么

MCP 使用 client ID、client secret 和 refresh token，向 LWA 换取短期 access token，并把 access token 用于 SP-API 请求。该步骤由代码完成，不需要每天在对话中粘贴 access token。[官方连接说明](https://developer-docs.amazon/sp-api/docs/connecting-to-the-selling-partner-api)

本项目不会帮你注册 Amazon 应用、完成身份审核或自动产生卖家 refresh token。它从已有授权开始工作。

## 4. 找到卖家、站点和区域

| 配置 | 来源或核对方式 |
| --- | --- |
| sellerId | 目标卖家的 Seller ID / Merchant Token，不能填店铺名称、ASIN 或应用 ID |
| marketplaceId | 目标国家站点 ID；成功连接后用 amazon_marketplaces_list 核对实际参与站点 |
| region | NA、EU 或 FE，按官方 SP-API 端点表选择 |

Seller ID 常见入口是 **设置 → 账户信息 → 业务信息 → 商家令牌**。Merchant Token 是卖家标识，不是 LWA refresh token。[Amazon 官方工作人员的查找说明](https://sellercentral.amazon.com/seller-forums/discussions/t/eb2bfdb3-c26c-424f-b32b-0cca441fb507)

美国站示例为 marketplaceId `ATVPDKIKX0DER`、region `NA`。其他站点不要直接照抄美国配置；区域与站点关系见 [官方端点表](https://developer-docs.amazon/sp-api/docs/sp-api-endpoints)。

## 5. 配置私有运行环境

以下命令在已克隆并构建的仓库根目录执行，不执行 skill:install。首次建立文件；已有 .env 或业务配置时保留并编辑，不覆盖原内容。

```powershell
Copy-Item -LiteralPath '.env.example' -Destination '.env'
Copy-Item -LiteralPath 'examples/live.config.json' -Destination 'amazon-ops.config.json'
```

Linux/macOS 可以分别用 cp 执行同样的复制。

### 5.1 .env

在你自己的私有环境里编辑，以下只展示变量结构：

```dotenv
AMAZON_LWA_CLIENT_ID=REPLACE_WITH_YOUR_LWA_CLIENT_ID
AMAZON_LWA_CLIENT_SECRET=REPLACE_WITH_YOUR_LWA_CLIENT_SECRET
AMAZON_LWA_REFRESH_TOKEN=REPLACE_WITH_THIS_SELLERS_REFRESH_TOKEN
AMAZON_OPS_CONFIG=D:/projects/amazon-ops-pilot/amazon-ops.config.json
```

全部占位值都需要替换。生产也可以用运行环境的秘密管理注入这三个变量，而不在磁盘存放明文 .env；需按 Amazon 数据保护要求和自己的运行环境设置权限、保留与撤销机制。.env 示例不代表加密秘密存储方案。

不要让 Agent 读取并展示真实值来“检查配置”。确认变量存在并调用平台查询即可。首版不使用 Seller Central Cookie、AWS IAM 密钥或买家受限数据令牌。

### 5.2 先使用 live + disabled 配置

下面是完整配置的形状。替换实际卖家、返回的商品类型、授权人和你确定的业务范围；日期是格式示例，使用时填写真实且适当的未来截止时间：

```json
{
  "version": 1,
  "mode": "live",
  "sellerId": "REPLACE_WITH_YOUR_SELLER_ID",
  "marketplaceId": "ATVPDKIKX0DER",
  "region": "NA",
  "stateDirectory": ".amazon-ops",
  "policyMaxAgeDays": 7,
  "planTtlMinutes": 15,
  "writePolicy": {
    "mode": "disabled",
    "expiresAt": "2026-12-31T00:00:00.000Z",
    "maxDailySubmissions": 3,
    "authorizedBy": "REPLACE_WITH_ACTUAL_OPERATOR",
    "scope": {
      "skuPrefix": "MYBRAND-",
      "productTypes": ["REPLACE_WITH_ACTUAL_PRODUCT_TYPE"],
      "currency": "USD",
      "minPrice": 10,
      "maxPrice": 50,
      "maxQuantity": 20,
      "fulfillmentChannels": ["DEFAULT"]
    }
  },
  "customSkills": [
    {
      "name": "my-brand",
      "path": "custom-skills/my-brand/SKILL.md",
      "stages": ["selection", "listing", "operations", "review"]
    }
  ]
}
```

不使用自定义技能时把 customSkills 设为 `[]`；使用时先按 [使用指南](使用指南.md) 创建对应文件。

`DEFAULT` 仅用于这个 FBM 例子的渠道范围。采用 FBA 时，应按该商品当前定义和账号资格确认可用渠道，再在 scope 中登记；配置渠道不等于已经创建 FBA 货件或有可售库存。

价格、数量、复核期、计划期限和次数都是本项目控制参数，示例不代表适合你商品的经营建议或 Amazon 统一标准。

### 5.3 MCP 客户端连接生产配置

把下面示例路径全部换成实际绝对路径：

```json
{
  "mcpServers": {
    "amazon-ops-pilot": {
      "command": "node",
      "args": [
        "--env-file=D:/projects/amazon-ops-pilot/.env",
        "D:/projects/amazon-ops-pilot/dist/server.js"
      ],
      "env": {
        "AMAZON_OPS_CONFIG": "D:/projects/amazon-ops-pilot/amazon-ops.config.json"
      }
    }
  }
}
```

在宿主中重新连接 MCP。客户端 env 中已有的变量优先于 .env 同名值；CLI 与 MCP 必须指向同一个配置文件、同一卖家和同一状态目录，避免出现 CLI 找不到计划或授权不匹配。

## 6. 验证接入，不发布商品

让 Agent 按仓库主技能依次执行：

| 步骤 | 工具或命令 | 通过标志 |
| --- | --- | --- |
| 加载配置 | amazon_ops_status；或仓库根目录 npm run cli -- status | live、正确卖家/站点、writePolicy.mode=disabled |
| 实际测试授权 | amazon_marketplaces_list | LWA 与 SP-API 请求成功，目标站点 isParticipating=true |
| 找商品类型 | amazon_product_types_search | 返回与你商品匹配的候选类型 |
| 读取当前要求 | amazon_product_type_definition_get | 取得最新定义及字段信息 |
| 检查草稿 | amazon_listing_validate | 没有 ERROR，警告已被实际审阅 |

`status` 不会验证 Amazon 凭据是否有效，不能仅凭它返回 live 就说店铺连接成功。`isParticipating` 也不证明具体类目、品牌或商品已获准销售。

不能用 listing.demo.json 测生产：DEMO_PRODUCT 是本地模拟类型，其属性不代表真实类目的必填项。真实字段来自当前卖家、站点和商品类型的 PTD，预览调用 mode=VALIDATION_PREVIEW，不正式创建商品。[官方预览说明](https://developer-docs.amazon/sp-api/docs/preview-errors-before-creating-a-listing)

## 7. 准备第一款真实商品和任务

### 7.1 提供事实与证明

可在已被 Git 忽略的 `.amazon-ops/inputs/MYBRAND-001/` 下保存私有资料，或用你自己授权的私有资料系统。至少准备：

- 商品名称、品牌、型号、材质、尺寸、包装数量、标识码及其真实来源。
- 有使用权并满足目标类目要求的图片及可供 Amazon 访问的位置。
- 适用的认证、测试、标签、授权及规则复核记录。
- 采购、包装、运输、进口、平台、配送、广告与退货成本和周转安排。
- 实际供货、质检、可发数量、交期、配送与退货方案。

本项目不托管图片、不替代图片像素检查，也不自动证明认证或商标权有效。图片 URL 应能按平台要求被访问；使用需登录才能打开的内部链接通常不能作为商品图片来源。

### 7.2 建立并推进阶段

Agent 调用 `amazon_workflow_start` 建立真实 SKU 的任务，保存返回的 runId。逐阶段核对真实资料后调用 amazon_workflow_advance；同一 SKU 不重复创建任务。

普通阶段的 evidence 形状：

```json
{
  "confirmed": true,
  "reference": ".amazon-ops/inputs/MYBRAND-001/商品事实.md",
  "notes": "填写本阶段实际完成的核对结论"
}
```

合规阶段在此基础上增加 reviewedAt 和 policySources，例如下面仅说明格式：

```json
{
  "confirmed": true,
  "reference": ".amazon-ops/inputs/MYBRAND-001/合规核对.md",
  "reviewedAt": "2026-11-14T00:00:00.000Z",
  "policySources": ["https://sellercentral.amazon.com/help/hub/reference/external/G200390640"],
  "notes": "填写本次商品、站点和材料的真实复核结论"
}
```

日期、引用和链接必须反映实际核对，不能照抄示例来代替复核。工具检查输入与已有状态，不证明资料内容真实；用户技能也不能替代证明。

到 listing 阶段后，Agent 读取当前用户技能，查询实际商品类型与字段，按资料生成完整 body，再调用 validate 和 prepare。`amazon_listing_prepare` 返回 planId、digest、expiresAt、预览和正文，先审阅这些内容。

## 8. 选择逐单发布还是自动发布

### 8.1 首次逐单授权：approval

执行顺序必须是：

1. 用户将 writePolicy.mode 设为 approval，填写实际范围、授权人和未来截止时间。
2. 重启 MCP，核对新配置。
3. 在原任务 listing 阶段重新调用 prepare，生成基于新配置的计划。
4. 操作者审阅计划，使用相同配置运行一次性授权命令。
5. Agent 调用 publish，之后 verify。

在仓库根目录，替换 PLAN_ID 与操作者名称：

```bash
npm run cli -- show-plan --plan PLAN_ID
npm run cli -- approve --plan PLAN_ID --by operator-name
```

使用非默认配置时，两个命令都加 `--config` 和同一个实际路径。approve 只写入一次性本机授权，不会提交商品。MCP 没有让模型自我批准的工具；授权人字段也不是身份认证系统。

### 8.2 授权范围内自动上架：bounded

用户明确授权自动执行后，在同一配置中把 writePolicy.mode 设为 bounded，并确认这些值：

| 字段 | 实际控制 |
| --- | --- |
| sellerId、marketplaceId、region | 本实例的卖家、站点与区域 |
| skuPrefix | 只允许此前缀的新 SKU，大小写按字符串匹配 |
| productTypes | 只允许已核实的类型列表 |
| currency、minPrice、maxPrice | 所有常规 our_price 的币种与价格范围 |
| maxQuantity | 本次正文提交的库存数量之和上限，不是店铺总库存上限 |
| fulfillmentChannels | 本次允许提交的渠道 |
| expiresAt | 预授权结束时间，ISO UTC |
| maxDailySubmissions | UTC 自然日正式提交尝试次数，未知结果也计入 |
| authorizedBy | 授权记录中的实际操作者名称，不产生额外 Amazon 权限 |

重启 MCP，复用原 runId，但**重新 prepare**。配置摘要已经变化，不能直接 publish 原 disabled/approval 模式下的旧 planId。

之后在有效范围内，Agent 可连续完成每个已具备真实前置资料的新 SKU 的验证、准备、提交和回读，无需每件重新创建一次性授权。每款商品仍有独立任务与计划；不是绕过校验的批量接口。任一项越界或资料缺失时停止该项，不能自行改 scope。

### 8.3 自动执行时的实际工具顺序

```text
读取仓库主技能
→ amazon_ops_status
→ amazon_workflow_get（新品尚无任务则先 start）
→ 读取当前阶段登记的自定义技能
→ 核对前置证据并逐阶段推进到 listing
→ amazon_product_types_search / amazon_product_type_definition_get
→ 按真实事实生成 body
→ amazon_listing_validate
→ 修复 ERROR，实际复核 WARNING
→ amazon_listing_prepare
→ amazon_listing_publish(planId)
→ amazon_listing_verify(planId)
→ 核实履约、前台与后续阶段
```

publish 只接收 planId，不能临时传新价格或换正文。内容变更需重做计划；当前实现使用新 SKU 检查来防止整体覆盖已有商品，仍应避免其他系统同时操作同一 SKU。

## 9. 提交后怎么判断结果

| 返回或现象 | 含义与动作 |
| --- | --- |
| plan.status=accepted | 平台已接收，保存 submissionId，继续回读 |
| verify.buyable=true 且 hasErrors=false | 该次回读时目标站点可买且未见错误，仍核对前台与履约 |
| accepted 但不可售 | 检查异步问题、库存、类目/品牌资格、配送准备，不反复 PUT |
| invalid | 依据明确问题修复草稿，重新准备 |
| unknown / submitting | 提交结果未确认，停止该 SKU 写入并人工核对，不能另建任务绕过去重 |

平台接收与后续可售不同，官方也要求处理异步问题。[Listing 生命周期说明](https://developer-docs.amazon/sp-api/docs/building-listings-management-workflows-guide)

publish 不会自动推进整个业务任务：在 listing 阶段用真实接收回执完成 advance，再核实 fulfillment 并 advance，进入 launch 后最近五分钟内 verify 确认可售及无错误，才完成启动阶段。FBA 入仓/广告等首版人工环节要保留实际回执。

## 10. 常见问题与停止自动化

| 问题 | 排查或恢复 |
| --- | --- |
| Agent 没有 amazon_* 工具 | MCP 客户端未连接或进程启动失败，先查 Node、dist 和绝对路径 |
| CREDENTIALS_MISSING | live 模式缺少三个 LWA 环境变量；只核对存在性，不展示真实值 |
| LWA_AUTH | 核对同一应用的 client ID/secret 与对应卖家 refresh token、授权及撤销状态 |
| AMAZON_HTTP 403 | 查应用角色、卖家授权、账号和区域；不是改 bounded 就能解决 |
| MARKETPLACE_NOT_PARTICIPATING | 查询参与站点，纠正账号/站点/区域，不能伪造返回值 |
| SKU_EXISTS | 首版不更新已有 SKU，人工检查，不换编号掩盖重复商品 |
| WORKFLOW_GATE / POLICY_STALE | 补真实证据；合规实际复核后用 refresh_compliance 更新 |
| PLAN_EXPIRED / CONFIG_CHANGED / SCHEMA_CHANGED | 重新获取定义、预览和准备，旧授权不沿用 |
| APPROVAL_REQUIRED / WRITE_DISABLED / 范围错误 | 查实际发布策略和授权，不让模型修改配置来绕过 |
| CLI 找不到计划 | 查 CLI 和 MCP 的配置路径、模式及状态目录是否相同 |
| STORE_LOCKED | 确认是否有活跃进程；不抢锁，不删除状态重跑 |

停止后续写入可将 writePolicy.mode 改为 disabled 并重启或断开 MCP。已发给平台的请求不会因此撤回；下架、撤销授权和处理退款需在对应系统完成。首版不自动执行这些操作。

保持代码、配置、凭据和状态在可信执行环境；能任意修改这些文件的主体也能改变本机控制规则。多租户服务需要独立服务端身份、秘密管理及隔离，不能依靠一个 authorizedBy 字符串实现。

## 11. 如果要服务其他卖家

使用适用的公开应用注册和 OAuth 授权流程。通常需要已登记的登录/回调地址、生成和核对 state、接收 selling_partner_id 与授权码、在有效期内换取 refresh token、关联并安全保存每个卖家的授权。[官方网站授权流程](https://developer-docs.amazon/sp-api/docs/website-authorization-workflow)

这个仓库目前没有 OAuth 回调服务器、租户账号系统或令牌数据库。不能把 GitHub Pages、仓库 URL 或 stdio MCP 进程当成上述回调服务，也不提供复制一条链接就自动接入第三方卖家的功能。需要先实现并验收该授权服务，遵循 Amazon 审核及应用发布要求；已合法取得授权的单卖家配置仍可由独立实例运行。
